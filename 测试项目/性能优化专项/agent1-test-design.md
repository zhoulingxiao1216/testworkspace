# Agent1 测试设计：三组全量优化项

> 依据文件：`claude-plan.md`
> 设计范围：覆盖第一组 1.1 至 1.12、第二组 2.1 至 2.13、第三组 3.1 至 3.12。
> 约束说明：本设计只根据计划文件整理，不读取、不推断真实代码实现。

## 1. 范围

本设计覆盖三组全部优化项：

- 第一组：资金交易与数据一致性，覆盖支付回调幂等、支付入口归属、Stripe 充值入账、余额原子化、发货运费判断、业务单号唯一化、队列补偿、生产配置、日志脱敏、导出拉图、迁移资产、双库迁移兼容。
- 第二组：购物结算链路与接入安全，覆盖购物车/报价/FJX/附加项结算链路、归属收口、CORS、开放接口鉴权、Token、RBAC、账号会话、验证码、下载 token、分页 clamp。
- 第三组：数据与性能基础设施，覆盖运行时 DDL、聊天分表、仓储入库、发货 N+1、商品详情写库、Redis 清理、首页缓存、月表索引、动态表名、上传策略、外部抓取、前端构建与 WMS。

不覆盖：

- 已完成项 F1 至 F7。

## 4. 第一组 P0 用例设计

### 1.5 发货运费条件赋值 bug

| ID | 场景 | 步骤 | 预期 |
|---|---|---|---|
| A5-001 | 运费相等 | 构造 `total_fee = before_total_fee` 的发货单并触发运费处理 | 不触发补缴、不触发退款；余额和流水不新增异常记录 |
| A5-002 | 运费增加 | 构造 `total_fee > before_total_fee` | 只触发补缴链路；补缴金额等于差额；流水、通知金额一致 |
| A5-003 | 运费减少 | 构造 `total_fee < before_total_fee` | 只触发退款链路；退款金额等于差额；流水、通知金额一致 |
| A5-004 | 小数精度 | 使用 0.01、0.10、10.00、10.000 等金额 | 使用金额精度比较，不因浮点误差误判 |
| A5-005 | 回归保护 | 连续处理同一发货单两次 | 不重复扣款、不重复退款、不重复通知 |

### 1.1 支付回调幂等与已收款补偿

| ID | 场景 | 步骤 | 预期 |
|---|---|---|---|
| A1-001 | 正常支付回调 | 触发支付成功回调 | 支付状态进入业务完成态，订单生成，报价/支付状态一致 |
| A1-002 | 重复回调 | 对同一支付单重复发送成功回调 2 次以上 | 只生成 1 次订单、1 组资金流水；响应稳定成功 |
| A1-003 | 提交后建单失败 | 模拟收款状态已提交，但 `createOrderFlow` 失败 | 状态停留在可补偿中间态，不被标为业务完成 |
| A1-004 | 补偿任务 | 对 A1-003 数据执行补偿 | 成功补建订单，状态进入业务完成态 |
| A1-005 | 已 paid 重试 | 对已收款未建单数据再次触发回调 | 不因 `paid` 直接跳过主流程；应进入补偿或继续业务处理 |
| A1-006 | 并发回调 | 同一支付单并发触发多次回调 | 无重复订单、无重复流水、无死锁；最终状态一致 |

### 1.4 余额原子化

| ID | 场景 | 步骤 | 预期 |
|---|---|---|---|
| A4-001 | 单笔充值 | 对用户 A 发起充值入账 | 余额增加，流水增加，流水金额和余额差额一致 |
| A4-002 | 单笔扣款 | 对用户 A 发起余额扣款 | 余额减少，流水增加，余额不得为负 |
| A4-003 | 余额不足扣款 | 对余额不足用户发起扣款 | 扣款失败，无余额变更，无成功流水 |
| A4-004 | 并发扣款 | 对同一余额账户并发发起多笔扣款 | 总扣款不超过可用余额，流水不重复，余额等于初始余额减成功扣款总额 |
| A4-005 | 并发充值和扣款 | 同一账户同时充值、扣款 | 最终余额与所有成功流水汇总一致 |
| A4-006 | 流水号唯一 | 高并发生成流水 | 流水号无重复，业务单号可追溯 |
| A4-007 | 事务回滚 | 模拟流水写入失败 | 余额不变化或整体回滚，无半成功数据 |
| A4-008 | 提现入口并发 | 同一用户并发提交提现或终审 | 不超扣余额，提现单、流水、余额一致 |
| A4-009 | 调账入口回归 | 后台对同一用户执行加款/扣款调账 | 余额变化与调账流水一致，失败时整体回滚 |
| A4-010 | 结算入口并发 | 多个结算任务同时处理同一账户 | 结算金额不重复、不遗漏，流水唯一 |
| A4-011 | 运费补缴/退款入口 | 运费补缴和退款触发余额变更 | 与 1.5 运费差额结果一致，余额和流水匹配 |
| A4-012 | 会员支付入口 | 使用余额支付会员或服务费 | 扣款原子化，余额不足时不生成成功流水 |

### 1.2 支付入口归属与重复支付单

| ID | 场景 | 步骤 | 预期 |
|---|---|---|---|
| A2-001 | 本人报价支付 | 用户 A 支付自己的报价单 | 支付单创建成功，归属为用户 A |
| A2-002 | 跨用户报价支付 | 用户 A 使用用户 B 的 `quote_no` 发起支付 | 请求失败，不创建支付单，不泄露用户 B 数据 |
| A2-003 | 同渠道单活 | 同一用户同一报价单重复发起支付 | 只保留一个有效 pending 支付单，重复请求返回既有单或明确失败 |
| A2-004 | 并发发起支付 | 同一报价单并发发起支付 | 不产生多条有效 pending 单，request_id 不重复 |
| A2-005 | request_id 唯一索引 | 根据环境确认 `payment_orders.request_id` 索引 | 唯一索引存在；若不存在，记录为上线阻塞项 |
| A2-006 | Context 键一致性 | 在 Workerman 场景下发起支付 | 能正确取得当前用户归属，不出现空用户或错用户 |

## 6. 第二组用例设计：购物结算链路与接入安全

### 2.1 报价回调越权删购物车 + 报价支付归属/行锁/整体事务

| ID | 场景 | 步骤 | 预期 |
|---|---|---|---|
| A7-001 | 本人报价成功回调 | 用户 A 报价成功后触发回调删除购物车明细 | 只删除用户 A 对应购物车明细，报价、扣款、删除在同一事务内完成 |
| A7-002 | 跨用户明细注入 | 用户 A 的报价回调参数中混入用户 B 的 `cart_detail_id` | 用户 B 明细不被删除，请求失败或忽略非法明细 |

## 9. 验收口径

- P0 用例全部通过，且无余额、流水、支付单、订单状态不一致。
- 并发类用例不得出现重复订单、重复流水、余额负数、余额覆盖。
- 支付和充值重复回调必须幂等。
- 跨用户支付必须失败，且不创建有效支付单。
- 跨用户购物车、报价、订单、发货、FJX 明细访问必须失败。
- CORS 不得反射非法 Origin，开放接口不得无签名访问。
- 后台动作级权限不得被直接调接口绕过。
- 商品详情、聊天、仓储核心请求不得在业务链路内执行 DDL 或高频表探测。
- 仓储、FJX、首页、Redis 等性能项必须有改造前后基线或明确 SQL/请求数上限。
- 敏感字段不得明文出现在日志、异常响应、导出任务日志中。
- 标注 `⏸` 的 1.2、1.7、1.12 必须完成环境确认；若无法确认，应列为上线风险。
- 第二组与第三组中涉及生产配置、数据库结构、缓存 key、构建产物的项目，若无法在环境验证，应列为上线风险。
- 所有失败补偿场景必须可定位、可重试或可人工处理。
