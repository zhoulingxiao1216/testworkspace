## ⚠️ Rule 4 逻辑挑战 — PRD 不确定性风险清单

> 以下为 PRD 中存在逻辑模糊或未定义行为的条目，**必须在开发/测试前与产品确认**。

### 风险 1：「模糊匹配」定义不明确

**PRD 原文**（§5.1.2）：
> IP地址搜索框 — 支持模糊搜索，输入不完整IP也能匹配

**逻辑不确定性**：

| # | 模糊场景 | 问题 | 风险等级 |
|:-:|:--|:--|:-:|
| 1 | 输入 `192` | 是否匹配 `192.168.1.1` 和 `10.192.0.1`？模糊范围是"前缀匹配"还是"任意子串包含"？ | 🔴 高 |
| 2 | 输入 `1.1` | 是否匹配 `192.168.1.1`、`10.1.1.1`、`1.1.0.0`？ | 🔴 高 |
| 3 | 输入 `.*` 或 `%` | 是否需要防范正则/SQL通配符注入？文档未提及 | 🟡 中 |
| 4 | IPv6 地址 | PRD 仅描述 IPv4，是否需要支持 IPv6？若有 IPv6 访问如何处理？ | 🟡 中 |
| 5 | IP 段/CIDR | PRD 仅提及"精确匹配和范围匹配"，是否支持 `192.168.1.0/24` 格式？范围匹配的具体语法未定义 | 🔴 高 |

**建议**：需产品明确"模糊搜索"是指**纯字符串 LIKE 包含**，还是支持 CIDR/网段匹配。两者的后端实现和测试策略完全不同。

### 风险 2：「一键采购自动选号」策略不明确

**PRD 原文**（§2.3, §5.3.4）：
> 系统自动选择可用的采购账号进行操作

**逻辑不确定性**：

| # | 模糊场景 | 问题 | 风险等级 |
|:-:|:--|:--|:-:|
| 1 | 选号策略 | "自动选择可用账号"的算法是什么？随机？轮询？按优先级？按负载均衡？ | 🔴 高 |
| 2 | 多账号可用 | 1688 有 3 个主账号各有子账号都绑定了，系统如何决定用哪个？ | 🔴 高 |
| 3 | 账号可用性判定 | "可用"的定义是什么？仅看 `status=启用`？还是还需验证 Token 有效性？ | 🔴 高 |
| 4 | 1688 vs 淘宝选择 | 一个订单的商品来自1688，系统是否自动识别平台并选择对应平台账号？跨平台商品如何处理？ | 🔴 高 |
| 5 | 账号并发 | 多个订单同时一键采购，是否存在账号锁竞争？同一账号能否并行处理多个采购任务？ | 🟡 中 |
| 6 | 失败重试 | 自动选号采购失败后，是否自动切换到下一个可用账号重试？重试次数有无上限？ | 🟡 中 |
| 7 | 子账号角色 | 1688 子账号是否有权限差异？某些子账号可能无采购权限 | 🟡 中 |

**建议**：需产品明确"自动选号"的选择算法（推荐：按优先级轮询 + Token 有效性预检），以及失败后的降级策略。

### 风险 4（Rule 8 逻辑挑战）：数据库绕过互斥开关后的系统自救

**挑战背景**：
> PRD 允许配置多个 1688/淘宝账号，但业务执行层要求「单点生效」。若开发人员或 DBA 直接操作数据库，绕过前端互斥开关，导致同一平台出现 >= 2 个 `status = 启用` 的账号，系统将面临「选号混乱」风险。

**PRD 已更新项**（2026-04-11 同步）：

| # | 挑战点 | PRD 现状 | 风险等级 |
|:-:|:--|:--|:-:|
| 1 | ✅ 互斥约束已声明 | PRD §5.3/§5.5 已明确：同一B2B后台账号下所有1688和淘宝采购账号只能有一个启用状态，启用B时自动禁用其他 | ✅ 已解决 |
| 2 | 无脏数据防御 | PRD 仍未定义数据库层面出现多个启用账号时的自救机制 | 🔴 高 |
| 3 | 部分解决 | PRD §7 新增表结构定义，但未设计 UNIQUE INDEX 或 CHECK CONSTRAINT | 🟡 中 |
| 4 | 采购归属不可追溯 | 一键采购成功后，PRD 未要求记录「本次使用了哪个具体账号」，多账号场景下无法审计 | 🟡 中 |
| 5 | 并发竞态 | 两个管理员同时操作不同账号的启用开关，事务不隔离可能导致双启用 | 🟡 中 |

**Rule 8 自救协议建议**（已更新为跨平台互斥）：
> 一键采购选号时，业务层**先执行断言** `COUNT(status=启用 AND b2b_admin_id=当前操作者B2B账号ID) == 1`：
> - `== 1` -> 正常选号执行
> - `== 0` -> 报错"未配置可用账号"
> - `>= 2` -> **拒绝执行 + 抛出告警 + 记录脏数据日志**，严禁"随机取一个"执行

## 测试核心原则（必读）

**原则 1：准入优先级链不可违反（Rule 5 - Trust Override）**
- 判定优先级：`授信豁免` > `黑名单拦截` > `白名单放行` > `普通IP拦截`
- 高优先级判定结果不可被低优先级覆盖

**原则 2：三方一致性必须闭环（Rule 5 - Three-Way Consistency）**
- 所有准入判定需验证：后台配置 ↔ 数据库/缓存 ↔ 前端反馈

**原则 3：中间件层物理拦截（Rule 6 - Middleware Lockdown）**
- 未授权 IP 必须在中间件层重定向，不可绕过 API 直连后台

**原则 4：平台隔离（Rule 6 - Account Sandbox）**
- 1688 与淘宝 Token/授权链路物理隔离

**原则 5：应用绑定硬约束（Rule 6 - App-Limit）**
- 1 个 1688 应用最多绑定 5 个主账号

**原则 6：单点生效与脏数据自救（Rule 8 - Single-Active）**
- 同一B2B后台账号下同一时刻只能有 1 个启用采购账号（跨1688/淘宝平台互斥）
- 检测到多启用账号（脏数据）时，系统必须拒绝执行并抛出告警，严禁随机取号
- 每笔采购必须记录具体使用的账号 ID
