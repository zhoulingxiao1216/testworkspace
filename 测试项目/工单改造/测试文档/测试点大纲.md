## 二、核心测试原则

- **原则1：状态机优先**
  - 所有动作必须围绕待处理、待客户确认、客户已回复、客户已确认、已完结验证，不能只看按钮是否存在。
  - 状态变化必须验证当前处理人、待办归属、历史记录和操作日志同步变化。

- **原则2：权限后端兜底**
  - 业务发送客户、当前处理人提交/转交、发起人完结、全部工单和历史工单数据权限都必须验证接口拒绝。
  - 前端隐藏按钮只能作为 UI 断言，不能替代后端权限结论。

- **原则3：商品快照和展示序号分离**
  - 工单绑定商品行和创建时快照；商品删除、拆分、合并后历史仍可追溯。
  - 展示序号 `001/002/003` 不是内部唯一ID，接口必须使用内部ID。

- **原则4：客户沟通不可跳步**
  - 只有业务可对客发送；客户回复后必须先翻译并同步，不能直接完结。
  - 多轮沟通不得重复展示，重复回调不得重复生成状态记录。

- **原则5：历史工单可召回但不可越权**
  - 同规格不同商品ID应可召回，近似规格不应误召回。
  - 无权限订单不得通过同规格历史工单或全部工单模式暴露。

- **原则6：模板与附件需保留历史证据**
  - 创建工单只回填中文模板；业务对客发送才读取客户语言。
  - 模板停用/删除/修改不能影响历史快照；附件必须保留分组、来源、预览和删除证据。

## 五、2026-07-14 技术落地更新补充

> 来源：`新工单重构设计清单.md` 2026-07-14 更新。该部分作为 Agent1 追加检查点，用于补齐实现层、接口契约和静态检查风险。

| 补充维度 | 必测检查点 | 风险说明 |
| --- | --- | --- |
| 新旧实现隔离 | 新工单不复用旧工单接口、旧状态机、旧表结构和旧 `WorkOrderLog`；旧客户确认页 `/user/todo/question` 不删除。 | 新旧流程混用会造成状态和历史记录错乱，且可能影响现有客户确认链路。 |
| 订单商品行摘要 | `orderProductSummary` 或等价聚合能力必须批量按订单/商品行返回工单摘要；聚合字段不落入订单商品表。 | 循环查库会导致订单详情性能风险；冗余字段落库会产生状态不一致。 |
| 数据库结构 | 新表需包含 `uuid`、`date`、`created_at`、`updated_at`、`status`；删除走 `status = 0` 或约定软删；`display_no` 仅展示，接口使用内部 UUID。 | 字段或索引缺失会影响追溯、软删、并发和跨商品编号冲突。 |
| 接口契约 | 所有接口统一 `{ code, msg, data }`；分页统一 `page/pageSize` 和 `list/total`；错误场景不得产生副作用。 | 契约不一致会增加前端特殊处理，错误请求可能写入脏数据。 |
| 待办角标与去重 | `todoBadge` 只统计当前登录人待处理；未处理待办按 `work_order_uuid + admin_id + todo_type + status` 去重。 | 重复回调、重复同步或转交可能导致待办数量膨胀。 |
| 代码落点和静态检查 | 后端在 `api-all`，管理端在 `admin-all-view`，用户端只做必要承接；执行 `git diff --check`、局部语法/lint，检索无新增旧依赖。 | 代码落点错误或未做静态检查会增加联调和回归风险。 |
