# 收费体系调整 - 架构级需求摘要

## 1. 业务愿景与核心痛点
- **现状痛点**：前后台金额口径不一致，前台多次展示“会员价”“单价”，后台不同页面使用不同单价快照，清算时容易引起争议；第三方平台服务费与代采手续费概念混淆；缺乏统一的节省额度感知体系。
- **业务愿景**：统一全量链路的商品价格基准（使用 1688 营销价 `promotionPrice`），统一订单清算核心公式，建立前中后台完全一致的报价、支付、采购、清算、多退少补展示和清算记录追溯闭环。同时提升“Hubbuyer 为您节省”透明度，赋能销售转化。

## 2. 核心规则重塑
1. **全局价格基准（MANDATORY）**：
   - 彻底废弃以往混合来源的“旧商品单价”。
   - 会员价（Hubbuyer价格）、前台商品单价、后台订单/报价/采购/全商品/入库/发货等**一切**带有“单价”属性的字段（涵盖页面回显、明细、表单下载、导出、打印），**全局强制取 1688 接口返回的营销价 `promotionPrice`**。
2. **运费与节省逻辑**：
   - **预估国内运费**：在商品详情和购物车阶段调用 1688 `product.freight.estimate` 预估运费；接口失败时标为“待确认”阻断错误入账。
   - **金额节省口径**：`商品金额节省 = 1688 原价对应金额 - Hubbuyer 会员价对应金额`（纯权益感知，不重复抵扣）；`人工交涉节省 = 正品金额 + 店铺退款 + 国内运费 - 实际支出 + 店铺返现`，独立展示，不进入实际清算金额。
3. **清算逻辑优化（2026-07-21 新增，以清算逻辑优化 PRD 为准）**：
   - `报价单支付金额 = 商品金额 + 预估国内运费 + 预估检品费用 + 预估附加项费用 + 预估代采手续费`。
   - `实际清算金额 = 实际支出 + 到付运费 + 退换货运费 + 店铺其他费用 + 实际检品费用 + 实际附加项费用 + 订单其他费用 + 实际代采手续费 - 店铺退款 - 店铺返现`。
   - `订单差额 = 报价单支付金额 - 实际清算金额`。
   - 订单差额 > 0 展示应退还客户，< 0 展示客户需补，= 0 无需处理。
   - 人工交涉节省只展示计算结果，不再作为采购差额参与订单差额扣减。
4. **名词分离**：
   - “手续费”专指 Hubbuyer 收取的“代采手续费”。
   - “平台服务费”专指第三方支付通道费用，不计入报价单支付金额。

## 3. 架构级影响面
- **前台展示层**：商品卡片统一样式；商品详情、购物车、确认订单、报价单、订单详情结构更新；新增固定文案的多语言适配。
- **快照与存储层**：购物车和确认订单阶段必须持久化 `promotionPrice` 单价快照、原价快照及预估运费快照，且后续链路防篡改。
- **资金清算层**：后台清算弹窗作为统一算力枢纽，执行重新计算、确认清算和结果留存；退款通道、资金执行、导出文件格式属于本次页面级 PRD 范围外，测试只验证页面结果、权限、历史记录与追溯。

## 4. 潜在风险点预警（审计提示）
- 1688 接口返回异常或无 `promotionPrice` 时的空态降级必须被严格处理，防止旧单价污染报价单。
- 店铺明细抽屉中的各分组费用汇总必须与订单维度的费用一览严格咬合。
- 多处页面（如购物车、确认订单、报价单、后台下载件）必须完全基于同一数据源快照，测试时需强检验跨端一致性。
- 新清算逻辑上线后，旧公式 `实际结算金额 - 报价单支付金额 - 采购差额` 不得继续用于前台订单详情、订单清算抽屉、订单清算记录或导出字段。
- 已清算历史订单不得因打开、查询或查看公式被自动重算；未清算历史订单缺少必要金额时必须禁止确认。
