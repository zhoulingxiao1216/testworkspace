## 1. 测试背景与目标

### 1.1 背景
全球站 B2B 站点需要在大促或推广前验证服务器承载能力，确认在目标在线规模下系统的吞吐、响应时间和稳定性满足要求。本次基于现有 Locust 压测工程（`全球站压测脚本/Performance`）在 main 环境开展。

### 1.2 测试目标
1. 验证系统可稳定支撑 **1000 个在线活跃用户** 的日常混合负载。
2. 找到系统的 **性能拐点（最大有效并发/吞吐）**，为容量规划提供依据。
3. 验证核心交易链路在压力下的正确性与稳定性：
   - 登录 → 商品浏览/搜索 → 加购 → **完整报价链路（附加项 Step1/Step2）** → 提交报价单 → **下载报价单（当轮 quote_no）**
4. 验证前台 SPA 页面级检查（免登录页 + 登录态页）在高并发下的可用性。
5. 暴露高并发下的瓶颈点（接口超时、错误率上升、资源饱和）。

### 1.3 目标量化口径
以"在线活跃用户"为输入，按并发模型换算到真实并发与吞吐：

| 指标 | 取值 | 说明 |
|:--|:--|:--|
| 在线活跃用户 | 1000 | Locust user 数（含思考时间） |
| 平均思考时间 | 1.25s | 脚本 `wait_time = between(0.5, 2.0)` |
| 预估并发率 | ≈ 19% | 响应时间 / (思考时间 + 响应时间) |
| 预估真实并发 | ≈ 190 | 1000 × 19% |
| 预估目标 RPS | ≈ 645 | 1000 / 1.55s 周期 |

> 换算公式：`并发数 = 在线用户数 × 并发率`，其中并发率由思考时间决定；`RPS = 在线用户数 / 单轮周期`。1000 user、190 并发、645 RPS 是同一负载的不同观测角度，不可重复打折。
>
> 注：完整报价链路单次下单涉及 7+ 个接口且含文件下载，实际下单任务耗时显著高于简化链路，RPS 估算以混合负载观测值为准。

## 2. 测试范围

### 2.1 被测接口与链路

#### 2.1.1 接口链路（API）

| 链路 | 用户类型 | 关键接口 | 是否写数据 | 默认开关 |
|:--|:--|:--|:--|:--|
| 登录 / 登录刷新 | 真实账号 | `POST /api/login/login` | 否 | 开 |
| 图搜浏览 | 真实账号 | `POST /api_ali/product/*` | 否 | 开 |
| 关键词搜索（1688） | 真实账号 / 虚拟账号 | `POST /api_ali/product/keyword` | 否 | 开 |
| 商品详情（1688） | 真实账号 | 1688 商品详情接口 | 否 | 开 |
| 关键词搜索（淘宝） | 真实账号 / 虚拟账号 | `POST /api_tb/product/keyword` | 否 | **关** |
| 商品详情（淘宝） | 真实账号 | `POST /api_tb/product/detail` | 否 | **关** |
| 浏览 + 加购（1688） | 真实账号 | `POST /api_b2b/cart/add1688`、`POST /api_b2b/cart/list` | 是 | 开 |
| 浏览 + 加购（淘宝） | 真实账号 | `POST /api_b2b/cart/addTb` | 是 | **关** |
| 完整报价链路 — 附加项 | 真实账号 | FJX：`getCheckFjxList` → `updateCheckFjx` → `getCheckFjxFeeTotal` | 是 | 随下单开 |
| 完整报价链路 — Step1 | 真实账号 | `POST /api_b2b/cartQuoteStep1/cartDetailList` | 否 | 随下单开 |
| 完整报价链路 — Step2 | 真实账号 | `POST /api_b2b/cartQuoteStep2/cartDetailList`、`cartDetailListTotalFee` | 否 | 随下单开 |
| 提交报价单 | 真实账号 | `POST /api_b2b/quote/create` | 是 | 可配 |
| 下载报价单 | 真实账号 | `GET /api_b2b/quotedetail/downQuote` | 否（仅校验响应） | 随下单开 |

**完整下单任务执行顺序（同一 Locust 用户、同一线程接力）：**

```
浏览 → 加购 → 购物车列表
  → 附加项列表/保存/费用合计（FJX）
  → 报价 Step1 明细 → 报价 Step2 明细/费用合计
  → quote/create（提取当轮 quote_no）
  → downQuote（使用当轮 quote_no，不落盘，仅校验 HTTP/文件体）
```

> 报价单下载检查点**不单独成 Locust 任务**，嵌套在「浏览 + 加购 + 提交报价单」任务内；「提交报价单」成功次数与「下载报价单」成功次数应大致相当。

#### 2.1.2 前台页面检查（UI，SPA 文档级）

| 页面 | 用户类型 | 路径 | 断言 |
|:--|:--|:--|:--|
| B2B 首页 | 虚拟账号 | `/` | HTTP 2xx + 标题含 `Hubbuyer \| B2B Sourcing Platform` |
| 关键词搜索结果页 | 虚拟账号 | `/Alibaba/list?key=...` | 同上 |
| 购物车 | 真实账号 | `/user/cart/index` | 同上（携带登录态 Cookie） |
| 购物车附加项 | 真实账号 | `/user/cart/additionalServices` | 同上 |
| 订单提交确认 | 真实账号 | `/user/cart/orderConfirm` | 同上 |

### 2.2 不在本次范围
- 支付链路（`/api_b2b/quote/pay`）真实扣款流程。
- D2C、插件加购、OEM 相关链路。
- 安全测试、稳定性 7×24 长稳测试（如需单列专项）。
- 第三方（1688 / 淘宝官方）上游接口的可用性，不计入本系统失败口径。
- 报价单 Excel **本地落盘保存**（压测脚本仅内存校验，不写入磁盘）。

### 2.3 淘宝链路说明
淘宝关键词/详情/加购默认**关闭**（`STRESS_ENABLE_TAOBAO_*=0`），避免 main 环境业务码 40000 等不稳定因素干扰基线压测。如需评估淘宝覆盖，须**单独开轮**并单列分析。

## 5. 用户模型与并发设计

### 5.1 两类用户与任务权重

| 用户类型 | Locust 类（全部模式） | 专用类（接口模式） | 行为 | 账号约束 |
|:--|:--|:--|:--|:--|
| 真实账号用户 | `HubbuyerStressUser` | `ApiRealUser` | 登录 + 浏览/搜索 + 加购 + 完整报价/下单/下载 + 登录态页面 | 占用账号池 |
| 虚拟账号用户 | `HubbuyerGuestBrowseUser` | `ApiGuestUser` | 页面访问 + 关键词搜索（只读） | 无需账号 |

**真实账号任务权重（`TASK_WEIGHTS`，数值越大调用概率越高）：**

| 任务 | 权重 | 说明 |
|:--|:--|:--|
| 仅浏览 | 6 | 图搜 / 1688 关键词（淘宝默认不参与） |
| 浏览 + 加购 | 3 | 加购后读购物车列表确认 |
| 登录态页面访问 | 2 | 购物车 / 附加项 / 订单确认页 |
| 浏览 + 加购 + 下单（含下载） | 1 | 低频重操作；下单成功后接力 downQuote |

### 5.2 1000 活跃用户的并发分配

按 B2B 站点"少数登录买家 + 多数匿名浏览"的真实比例，采用 **5% 真实 / 95% 虚拟**：

| 参数 | 取值 | 依据 |
|:--|:--|:--|
| 真实账号并发数 | 50 | 略高于可用 mock 池（48），允许轻度复用；严格一人一号时取 48 |
| 虚拟账号数量 | 950 | 承担只读浏览/搜索主流量 |
| 真实账号加载速率 | 5 /s | 平滑爬坡，约 10s 加载完真实用户 |
| 虚拟账号加载速率 | 50 /s | 约 19s 加载完虚拟用户 |
| 每链路浏览步数 | 2 | 默认 `STRESS_BROWSE_STEPS=2` |
| 加购链路 | 开启 | 验证写入链路 |
| 完整报价链路 | 随下单开启 | 默认 `STRESS_ENABLE_FULL_QUOTE_FLOW=1` |
| 报价单下载 | 随下单开启 | 默认 `STRESS_ENABLE_QUOTE_DOWNLOAD=1` |
| 提交报价单链路 | 阶梯前期关闭，单独小规模验证 | 控制 main 脏数据量 |

**推荐压测口径（与 2026-06-16 / 06-17 实测对齐）：**
- 接口压测：`locustfile_api.py`
- 1688 专属：淘宝三开关关闭
- 完整报价链路 + 下单后下载：开启

备选（写链路压力更大）：真实 100 / 虚拟 900（接受约 2 倍账号复用）。

## 6. 测试场景与策略

### 6.1 场景一：基准测试（Baseline）
- 1 个真实用户（建议 `performance_test_004@126.com`）+ 少量虚拟用户。
- 跑通完整链路：加购 → 附加项 → Step1/Step2 → 提交报价单 → 下载报价单。
- 记录各接口基线响应时间与成功率，作为后续对比基准。
- 可执行 `Performance/test_quote_download_chain.py` 做脚本级冒烟。

### 6.2 场景二：阶梯加压（核心，定位拐点）
逐级递增在线用户，每级稳定运行 3~5 分钟，观察吞吐与响应曲线拐点：

| 阶梯 | 在线用户 | 真实 / 虚拟 | 预估真实并发 | 预估 RPS |
|:--:|:--:|:--:|:--:|:--:|
| 1 | 200 | 20 / 180 | ≈ 38 | ≈ 130 |
| 2 | 400 | 30 / 370 | ≈ 76 | ≈ 258 |
| 3 | 600 | 40 / 560 | ≈ 114 | ≈ 387 |
| 4 | 800 | 48 / 752 | ≈ 152 | ≈ 516 |
| 5 | 1000 | 48 / 952 | ≈ 182 | ≈ 645 |

> 若在到达 1000 前 RPS 已停止增长、P95 陡升或错误率上升，则该点即为系统容量上限。

### 6.3 场景三：稳定性测试（可选）
- 在拐点并发的 70%~80% 下持续运行 30~60 分钟，观察有无内存泄漏、响应时间漂移、错误率累积。

### 6.4 场景四：峰值/容量验证
- 直接加载到 1000 在线用户，验证目标负载下系统是否满足通过标准。

## 7. 性能指标与通过标准

### 7.1 全局指标

| 指标 | 通过标准 | 说明 |
|:--|:--|:--|
| 事务成功率 | ≥ 99.9% | 仅统计系统侧失败，业务码异常单列分析 |
| 错误率（系统侧） | < 0.1% | 超时、5xx、连接拒绝 |
| RPS / TPS | 达到目标负载且未触顶 | 目标负载下吞吐稳定 |
| 服务器 CPU | ≤ 80% | 应用与数据库节点 |
| 资源 | 无持续 GC、无连接池耗尽、无队列堆积 | 监控侧观测 |

### 7.2 分接口响应时间（P95）

| 接口类型 | 通过标准（P95） | 规则阈值（脚本） |
|:--|:--|:--|
| 常规读接口（搜索/图搜/详情/购物车列表） | ≤ 3s | 5000ms |
| 加购 / 附加项保存 | ≤ 3s | 5000ms |
| 提交报价单 `quote/create` | ≤ 10s | 10000ms |
| 下载报价单 `downQuote` | ≤ 15s | 15000ms |
| 前台 SPA 页面 GET | ≤ 3s | — |

判定口径：
- **通过**：目标 1000 在线用户负载下，全部指标达标且无系统侧阻塞错误。
- **附条件通过**：核心指标达标，存在非阻塞的局部慢接口或可规避的业务问题，有跟进计划。
- **不通过**：目标负载未达到、错误率超标、核心链路失败或服务器资源饱和。

## 9. 监控与结果分析

- **压测端**：测试平台"性能压测"页的总览（RPS、P95、失败率）、失败页签、慢接口页签、请求明细；或 Locust HTML/CSV 报告。
- **服务端（需运维配合）**：应用与数据库节点的 CPU、内存、GC、慢 SQL、连接池、网络 I/O。
- **分析重点**：吞吐拐点、响应时间陡增点、错误类型分布、资源饱和先于哪个组件出现。
- **完整报价链路专项**：附加项列表/保存/费用合计、Step1/Step2 明细与费用合计、提交报价单、下载报价单应均为 0 失败；提交与下载次数应大致配对。

## 10. 风险与应对

| 风险 | 影响 | 应对 |
|:--|:--|:--|
| 淘宝接口在 main 返回业务码 40000 | 失败率虚高、拉低 RPS | **默认关闭**淘宝三开关；需评估时单独开轮并分列统计 |
| `performance_test_003` 登录 HTTP 500 | 预热固定失败 | 已从 main 池剔除；待后端修复 strtotime 空值后可恢复 |
| 真实账号写链路产生脏数据 | main 生成大量报价单/购物车数据 | 阶梯前期关闭下单链路；写链路单独小规模验证；测试后清理数据 |
| 完整报价链路 + 下载加重耗时 | 下单任务 P95 升高、RPS 低于简化链路预期 | 分析时按完整链路口径解读；不与简化链路历史数据直接横比 |
| 报价单下载仅内存校验 | 无法事后抽检 Excel 内容 | 如需留档须另行开启落盘（当前脚本不支持） |
| 压测机单进程 CPU 瓶颈 | 1000 用户压测端先饱和，数据失真 | 使用多进程 `--processes -1` 或分布式 worker |
| 账号复用导致限流 | 真实账号过度复用触发服务端限流 | 真实并发数 ≤ 账号池规模；需要更多则扩充 mock 账号 |
| 与其他测试争抢 main 环境 | 数据/负载相互干扰 | 提前协调环境窗口，独占压测时段 |
