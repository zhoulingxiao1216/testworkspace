# Agent 1 (测试设计师) 全生命周期启动引擎

> **执行提示**：本工作流专属服务于 **Agent 1 (测试设计师)**。当用户下发测试分析或用例设计任务时，Agent 1 必须严格遵循本文件中的 8 阶段流转。此时下文描述中的"引擎"即完全指代 Agent 1 本身。

**【前置加载】**
- **依赖清单**: Agent 1 启动工作流后，必须先读取 `.agent/dependencies.yaml`，并使用 `deps.<alias>` 解析本文所有依赖路径。
- **核心技能组**: 必须首要读取 `deps.skill_agent1_test_design` 获取完整的身份约束与阶段能力定义。
- **Memory 召回**: Agent 1 必须读取 `deps.memory_readme`，随后按项目名召回：
  - `deps.memory_shared_project_registry`
  - `deps.memory_shared_decision_log`
  - `deps.memory_shared_known_issues`
  - `deps.memory_agent1_design_patterns`
  - `deps.memory_agent1_requirement_audit`
  - `deps.memory_agent1_coverage_gap`
  - `deps.memory_exchange_needs_more_cases`
  - `deps.memory_exchange_remediation_log`
- **Memory 使用边界**: Memory 只作为召回上下文，不得覆盖当前 PRD、人工确认结论或 `deps.superpowers_base`。发现冲突时，以当前 PRD/人工确认结论为准，并将旧记忆标记为 stale 或写入 `deps.evolution_rejected_learnings`。

**【系统流转基座配置与远端权限管控】**

- **Superpower 基础规约**: `deps.superpowers_base`（全局通用测试规约，各项目通过 `inherits` 继承。包含 §1 Design First / §2 TDD Protocol / §3 Brainstorming 三大通用协议）
- **测试产出工作区**: `test_workspace`（映射自 Gitee 远端仓库：`义乌市协润进出口有限公司/global-test`）
  - **管控级别**：【读写权限 Read & Write】
  - **允许动作**：允许拉取（Pull）、本地创建修改、执行提交（Commit）以及**向远端推进（Push）**。
- **PRD需求拉取信源**: `deps.pm_docs_root/[目标模块名称]`（映射自 PM 远端仓库，执行时请指定为 `会员体系` 或其他模块名）
  - **管控级别**：【绝对只读 Read-Only】
  - **允许动作**：极限制于拉取和对比需求变更。**严格红线禁止**执行任何对该远端仓的修改、Commit 及 Push 操作。

Antigravity，请严格按照以下标准化的 **8 阶段流程**执行测试构建全生命周期流转，期间除非遇到阻塞性报错请连续执行。所有产出目录统一为 `deps.project_test_docs_dir_pattern` 对应目录，请依据环境路由完成跨库知识检索与落地。

**【全局抗击幻觉与隔离约束（反模版投毒）】**
1. **实体概念强隔离**：【测试点】仅特指验证业务的宏观大纲层级（绝无具体步骤或表格）；【测试用例】必须特指包含准确 `TC-` 编号与 5 行数据的微观表格体。两者在全盘逻辑中严格互斥，不得张冠李戴！
2. **反模版泄漏协议 (Anti-Leakage)**：您在检索或参考 `deps.global_specs_root` 目录下的规范文档时，遇到的任何极其真实的业务举例（如 `TC-FI-008 补差价` 等测试示例），**纯粹为展示所需版式的虚拟占位符！绝对禁止**产生思维幻觉并将这些占位符业务代入、输出到您正在处理的当前项目中。一切产出的业务描述必须且只能 100% 来源于当期 `deps.pm_docs_root` 拉取的真实 PRD。

**【阶段 1：状态判定与跨库版本映射】**
- 定向从 `deps.pm_docs_root` 源端拉取目标模块的最新 PRD 文档与业务拓扑。
- **[强制摘要产出]**：引擎在深度阅读 PRD 后，必须沉淀发版级的核心上下文。严禁将变更解读隐藏，须即刻生成一份独立、人类友好的文档落盘（增量更新模式下命名为 `测试文档/Vn_需求变更对齐摘要.md` 以沉淀核心 Delta；全新构建下命名为 `架构级需求摘要.md`），以此彻底根除业务方的"重提问"痛点。
- **[Base 前置校验]**：先确认 `deps.superpowers_base` 存在且包含 §1-§3 通用规则。若不存在则报错中断："全局基础规约缺失，请先执行 superpowers 体系初始化"。
- 扫描 `deps.project_test_docs_dir_pattern` 对应目录内的四大件产物（支持模糊匹配如 `*superpowers*.md`、`*大纲*.md`、`*用例*.md`、`*工期*.md`）存在情况，以此判定当前任务模式：
  - **模式 A【全新构建】**：目录为空或无对应匹配。完整执行阶段 2-7。
  - **模式 B【断点补全】**：存在部分文档。跳过已存在的基座生成，直接从缺失的最早一个产出环节介入。
  - **模式 C【增量更新】**：文档全部齐全。依据刚才提炼的变更摘要，在后续全程严丝合缝地附加【增量更新】行为流程。

**【阶段 2：需求漏洞与歧义断言（人工流转锚点）】**
- 引擎在解析新版本需求时，须发散思维进行逻辑死角与边界状态（如并发控制、数据流转闭环）审计。
- **分支判定：**
  - **[有漏洞/歧义]**：生成 `审计待确认问题单.md` 落盘，**强制挂起任务**。等待业务/开发人工答复并下发恢复指令后，将该工单合并为 `审计确认纪要.md` 继续流转。
  - **[无漏洞/歧义]**：控制台输出"未暴露业务风险，安全跳过审计层"，进入阶段 3。

**【阶段 3：Superpower 架构演进】**
- 提炼系统最高优先级的测试约束（强硬过滤机制、跨平台隔离等），生成/更新 `deps.project_superpowers_pattern`。
- **[继承架构感知（强制约束）]**：
  - 生成前必须先读取 `deps.superpowers_base`，确认通用规则（§1-§3）已存在。
  - 项目 superpowers.md 中**严禁重复定义** base 中已有的通用规则（§1 Design First / §2 TDD / §3 Brainstorming），仅通过头部 `inherits: superpowers-base` 声明继承，并在正文 blockquote 中注明继承来源及领域审计补充。
  - 领域规则编号从 §4 起始，保持连续无跳跃。
- **[YAML Frontmatter 强制规范]**：生成的 superpowers.md 必须包含标准 YAML frontmatter（name / description / version / domain / inherits / triggers），且每条领域规则必须标注 `🔫 触发` 行内标签以支持按需激活。若当前项目不涉及某些高阶规则域，必须在 frontmatter 中通过 `unloaded_rules` 显式声明卸载。
- **[规则依赖图]**：在 frontmatter 之后、领域规则之前，必须添加 Mermaid 格式的规则依赖流程图，并附"执行约束：严禁在未通过前置规则校验的情况下执行后置规则的审计逻辑"声明。
- **[测试数据画像显性化]**：在文件内单独增加【测试数据画像与隔离策略】模块，强制识别并定义完成本轮测试必备的极简最小数据集与账号隔离要求（如：1个新注册白板号、1个B2B高权限号），彻底杜绝后续因前置条件不清导致的用例互相交叉污染。
- **[局部字典隔离挂载]**：您必须依据当前 PRD 推导该项目的全部微服务/业务域，并在 `superpowers.md` 内生成该项目的专属**【模块缩写配置表】**（例如定义 `IM-AUTH: 准入验证`, `IM-CHAT: 核心聊天`），作为全量测试资产挂载的唯一合法声明字典。
- **（增量更新特征）**：文件尾部必须单独追加《本次版本变更规则影响面评估》，且**必须采用结构化表格**（表头：影响域 / 变更内容 / 受影响模块 / 测试策略调整 / 新增用例估算），严禁使用散文体描述。

**【阶段 4：测试大纲构建与特征打标】**
- 结合 PRD 细节与确定的 superpower 约束，结构化整理对应的 `deps.project_test_outline_pattern`。
- **（断点补全特征）**：若文件已存在，只读取状态。
- **（增量更新特征）**：不轻易推翻大纲原有脉络，仅针对被修改或扩充的关键点附加 `*[V2变更]*` / `*[新增]*` 溯源标签。

**【阶段 5：测试用例实例化】**
- 将宏观大纲精细剥离，生成执行粒度的 `deps.project_test_cases_pattern`。
- **[绝对语法硬约束]**：请严格遵守以下格式生成，绝不自由发挥：
  1. **层级必备**：在输出每个具体的测试点之前，**必须先输出一行二级或三级标题作为分类大纲（如 `## 1.1 未登录状态拦截`）**。其下再连续跟该测试点的详尽测试用例。
  2. **唯一精确锚点**：每条用例必须以 `#### TC-{模块缩写}-{三位流水号} 【{类型}】{用例标题}` 为唯一精确锚点起手。**警告：此处的 `{模块缩写}` 必须严丝合缝地只从您在【阶段 3】写进 `superpowers.md` 的专属【模块缩写配置表】中读取（位于 YAML frontmatter 之后的正文段落）！绝不允许在此刻凭空发明未声明过的野鸡前缀！**
  3. **表格与换行死线**：用例体必须且仅限一张二维表（包含 测试点、优先级、前置条件、操作步骤、预期结果）。**严禁使用无序列表，严禁在表格内敲击真实回车 `\n`，多步骤必须用 `<br>` 分隔。**
  4. **[自动化 P0/SmokeTest 锚定]**：在填写表格的"优先级"时，引擎必须判定：若该用例直接关联（或触碰）了【阶段 3】提取的高危规则或资金核心流转，**强制将其优先级评定为 `Critical`，并在标题尾部追加物理防线标签 `[SmokeTest]`**，以为后续的 CI/CD 自动化冒烟大盘提供抓取锚点。
- **（断点补全特征）**：若文件已存在，只读取状态。
- **（增量更新特征）**：受到 PRD 变更约束而失效的旧有用例，严禁直接采取删除处理，必须将其置为 `[已废弃-受xxxx影响退场]` 状态，保留追溯轨迹。

**【阶段 6：用例与高危规则双向反射评审】**
- 阶段 5 完毕后，引擎必须对生成的用例与 **`deps.superpowers_base` + `deps.project_superpowers_pattern`** 进行双层交叉审计：
  - **Base 层审计**：确保 TDD 协议（§2）在用例结构中得到体现（Red→Green→Refactor 流程可追溯），Brainstorming（§3）的边界值审计要求在用例中有对应覆盖。
  - **领域层审计**：确保涉及高危业务原子（如"账号互斥事务"、"最高权限沙箱"、"授信强行覆盖"、"身份-计费锚定"等）的每条规则，在用例池中找到至少 1:1 的验证映射体，确保无任何脱漏。
  - **依赖链审计**：按 `superpowers.md` 中的 Mermaid 规则依赖图顺序，验证前置规则的用例在文档中排列于后置规则用例之前（或在前置条件中显式标注依赖关系）。

**【阶段 7：结构化工期模型评估】**
- 依据全量用例及环境要求量化转化，并强制采用以下四大模块的表格化结构输出到 `deps.project_test_docs_dir_pattern`：
  1. `一、测试工时明细`（表头：测试模块/基础测试点/扩展后用例数/预估工时）
  2. `二、总工期汇总`（表头：阶段/说明/工日）
  3. `三、分轮执行策略`（表头：轮次/范围/用例数/目标）
  4. `四、重点说明`（罗列重度前置环境、跨平台物理隔离测试等要求）
- **（增量更新特征）**：在原有工期预算上，强制单列"手工测试新增拆零工时"与因架构异动带来的"防回归战略储备工时"。

**【阶段 7.5：结构化交接清单 (Structured Handoff Manifest)】**
- 阶段 5 实例化测试用例完成后，必须提取用例元数据，额外输出一份 `deps.project_handoff_manifest_pattern`。
- 该清单供 Agent 2 直接读取，必须包含：
  1. `total_cases`: 用例总数
  2. `priority_distribution`: 各优先级（Critical/High/Medium/Low）分布统计
  3. `env_requirements`: 前置环境与测试账号要求汇总
  4. `estimated_time`: 预估执行总时长
  5. `execution_queue`: 各模块 TC 编号的执行顺序大纲

**【阶段 7.6：Memory 沉淀与自进化候选】**
- 在完成阶段 7.5 后，Agent 1 必须执行轻量复盘，并按以下边界沉淀：
  1. 可复用的需求审计经验 → `deps.memory_agent1_requirement_audit`
  2. 可复用的用例设计模式 → `deps.memory_agent1_design_patterns`
  3. 来自执行或评审的覆盖缺口 → `deps.memory_agent1_coverage_gap`
  4. 需要 Agent 2 复审或执行关注的交接项 → `deps.memory_exchange_remediation_log`
  5. 达到晋升条件的稳定经验 → `deps.evolution_promotion_candidates`
- 严禁将一次性猜测直接写入 skill/workflow。严禁在 memory 中存储密码、Token、Cookie、私钥或原始客户数据。

**【阶段 8：最终验收评审（按需唤醒）】**
- **唤醒口令**：当用户下发类似"输出 [XX项目] 的测试报告"指令时独立触发。
- 引擎必须先加载 `deps.acceptance_report_spec`。
- 引擎将拉取该项目下的 `工期评估.md`、`执行交接清单.yaml`、`superpowers.md`、`测试点大纲.md`、测试用例 Excel/Markdown、缺陷 RTF，以及 Agent 2 生成的全部 `执行报告_*.md` 和 `缺陷清单_*.md`。
- 遵循上线验收测试报告规范，自动聚合成包含【测试覆盖度】、【执行率统计】、【缺陷闭环】、【业务防线审计】及【定级发布建议】的 Markdown 与 PDF 上线验收测试报告。

**【终止通告动作】**
- 在控制台绘制最终 `测试文档/` 树状文件拓扑图。
- 输出本轮 Memory 更新摘要：列明写入了哪些 memory 文件；若无新经验，明确说明"本轮无新增可复用记忆"。
- 声明通告："本次执行已成功完成 [断点补全/全新构建/增量更新] 流转。"
