# 需求歧义与并发逻辑盲区审计单 (Phase 1.5)

在对比 PRD 详述与现有 Superpowers 架构时，测试引擎的高级扫描捕捉到了以下 5 项可能诱发线上事故的「深水区缺陷」。这类问题可能导致业务雪崩或安全失效，必须在进入下一阶段进行大纲重构前得到您的确切规则敲定：

## 1. 【高危·并发死锁】采购账号的“并发启用”防线穿透
* **问题描述**：PRD 5.3 节要求“同一B2B账号下只能有 1 个启用状态的采购账号。当启用A时，自动禁用其他”。但是当恶意用户或采购员在多开的浏览器标签页，或者处于网络高峰期**并发地（同毫秒级极高并发）对多个账号同时发送“启用”请求**时，极有可能突破简单的业务表单禁用，导致数据库涌入两个以上并存的启用状态，直接穿透单例约束。
* **确认诉求**：请问系统到底是在数据库层面加了类似唯一联合索引的强约束机制？还是代码里上了分布式锁？测试用例是否需要覆盖**毫秒级并发启用测试**？

## 2. 【逻辑断层】1688“应用五账号上限”约束与表单字段缺失
* **问题描述**：PRD 在第四章明确警告“1个1688应用最多绑定5个主账号，支持多个应用”。但是在 5.4.1 [添加1688主账号弹窗] 的表单要素清单里（仅包含账号名称、账号ID、token、B2B后台账号、备注），**根本没有让管理员选择或输入“所属应用名/AppKey”的地方**。
* **确认诉求**：如果表单层缺失了“多应用关联字段”，系统是如何在物理底层计算“某一个特定应用是否超过了 5 个绑定量”这一强制限制的？是否需求在此处出现了模块断层？

## 3. 【死角盲区】订单维度的“一键采购”并发超买风险
* **问题描述**：PRD 5.9 设定：只需在“进行中”状态即可点击一键采购。假如 2 个采购专员在进行业务交接时发生冲突，同时在审同一笔大额代购订单，两人**极其并发地点击**了【一键采购】。
* **确认诉求**：针对“超买/重复发单”的死角，系统是通过我们独有的“采购号外联锁”进行订单锁定拦截（前置变成“下单中”状态阻断交互），还是依赖向下游 1688/淘宝 传递交易凭证来实现最终幂等控制机制？

## 4. 【逻辑闭环冲突】黑白名单权限下放默认体系的悖论
* **问题描述**：PRD 2.1 和 5.1 指出“不在黑白名单内则拦截提示无法访问（只白名单可进系统）”；但同时说黑白名单“禁用后变成普通IP，失去黑白名单功能”。这意味着一旦禁用任何成员，就等同于“没出现在名单内=被默认拦截”。这样让“黑名单IP将无法登录”单独分类显得非常冗余。
* **确认诉求**：“允许登录系统但一直强制弹不可关掉的软拦截页面” VS “直接在登录接口物理拒绝报 401/403”，这二者的场景设定区别在哪里？如果纯依靠白名单准入，那黑名单功能存在的核心必要性是什么？

## 5. 【信息缺漏】1688 账号的 Token 刷新机制断档
* **问题描述**：淘宝页面规则十分扎实，同时提到了 `AccessToken` 和 `RefreshToken` 可以续期。但在 1688 添加账号（5.4.1阶段）表单只收录了硬生生的 `token` 短字段。
* **确认诉求**：1688 的 Token 即将过期预警并发生过期时（如 30 天后），管理员是否只能手工删除原账号重新建档？如果删掉原账号重建，是否会导致以往绑定过该条数据外键的账单在关联溯源上出现悬空报错（Data Orphaning）？
