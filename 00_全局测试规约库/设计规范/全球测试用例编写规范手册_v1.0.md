# 测试用例编写规范手册 · 全球会员体系

> **版本**：v1.0  
> **生效日期**：2026-04-03  
> **适用范围**：全球会员体系优化项目所有测试用例（含手工用例与未来自动化解析用例）

---

## 一、结构化锚点规范

### 1.1 测试点分类层级（文档导览锚点必备）

每个独立的测试点在输出其第一个测试用例之前，**必须**输出一行二级或三级标题作为测试点分类大纲。这不仅帮助解析器（Parser）提取所属测试点，更用于在 Markdown 阅读器中自动生成右侧导航大纲（TOC）。

```markdown
### {编号} {测试点/模块名称}
```

### 1.2 用例块标题格式（Parser 精确锚点）

每一条用例必须以以下格式开头，作为单条用例边界的唯一精确锚点：

```markdown
#### TC-{模块代码}-{三位编号} 【{类型}】{用例标题}
```

**字段说明：**

| 字段 | 规则 | 示例 |
|:--|:--|:--|
| `TC` | 固定前缀，不可更改 | `TC` |
| `{模块代码}` | 大写字母+连字符，见模块代码表 | `MG` / `CL-CART` |
| `{三位编号}` | 三位数字，从 `001` 开始顺序递增 | `001` / `018` |
| `【{类型}】` | 必填，见类型枚举表 | `【正向】` / `【重点·异常】` |
| `{用例标题}` | 简短动宾结构，不超过 30 字 | `会员到期后价格自动降回非会员价` |

**模块代码申明规范（解耦设计）：**

> **架构约束**：作为全局测试宪法，本部规范**不硬编码**任何具体业务线的模块缩写（如 `MG = 会员系统` 等）。
> **落地执行**：各个业务线（如 IM 系统、采购系统、会员体系）的缩写对照表，**必须强制定向维护在各自独立工程目录下的** `测试文档/superpowers.md` 中或项目级字典表中。
> 在解析当前用例时，引擎应自动从该项目的顶级上下文中动态检索前缀定义，实现 100% 规则与业务解耦！

**类型枚举表：**

| 类型标签 | 含义 |
|:--|:--|
| `【正向】` | 标准正常流程验证 |
| `【异常】` | 错误输入、边界拦截验证 |
| `【重点·正向】` | 高风险但走正常流程 |
| `【重点·异常】` | 高风险且走异常路径 |
| `【Critical·{关键词}】` | 最高优先级，关键词说明场景（如 `Critical·Security`）|

## 二、必填字段矩阵

每条用例必须包含以下 **5 个标准表格行**，Parser 按字段名精确匹配，缺失任意字段判定为不合格用例：

```markdown
| 字段 | 内容 |
|:--|:--|
| **测试点** | {对应大纲测试点原文，或简短描述} |
| **优先级** | {Critical / High / Medium / Low} |
| **前置条件** | {执行此用例前必须满足的状态，含账号、数据、环境} |
| **操作步骤** | {步骤序号列表，使用 <br> 换行} |
| **预期结果** | {与步骤对应的系统预期表现} |
```

> [!IMPORTANT]
> 以下为可选扩展字段，出现时须使用相同表格行格式追加在必填字段之后：
> - `| **财务精度** | ... |`：涉及货币计算时必须追加
> - `| **关联客户端场景** | ... |`：管理端用例影响前台时追加
> - `| **备注** | ... |`：需业务确认或存在待定逻辑时追加

## 三、优先级判定标准

| 优先级 | 触发条件 | 举例 |
|:--|:--|:--|
| **Critical** | ① 涉及金额计算、汇率换算、财务精度 <br> ② 涉及安全鉴权（Token、越权、缓存清除）<br> ③ 会员等级转换的核心路径（升降级、到期）<br> ④ 数据不可逆操作（订单生成、资金入账）| 残值计算、汇率锁定、API越权熔断 |
| **High** | ① 核心业务流程的主干路径 <br> ② 前台可见的价格展示与拦截逻辑 <br> ③ 管理端启用/禁用的实时生效验证 | B2B拦截、附加项等级价、开关联动 |
| **Medium** | ① 用户体验类验证（视觉、排版、提示文案）<br> ② 管理端配置项的边界值测试（如5个上限）<br> ③ 非关键路径的正向流程 | 卡片横向滚动、期限套餐上限 |
| **Low** | ① 纯视觉回归 <br> ② 数量上限类的极端边界 <br> ③ 已有高级别用例覆盖的降级验证 | 添加按钮 6 次置灰验证 |

## 四、操作步骤书写规范

### 4.1 基础格式

- 步骤必须使用**数字序号**（`1.` `2.` `3.`），禁止使用字母序号或无序列表
- 多步骤在同一表格单元格内，使用 `<br>` 换行（不可换行为多行或使用 `\n`）
- 预期结果中，**多个预期项**同样使用数字序号 + `<br>` 换行

### 4.2 多场景步骤格式

当一条用例包含多个测试场景时，使用 `**场景X（描述）**：` 标注，再跟步骤序号：

```
| **操作步骤** | **场景一（低于底价）**：1. 填写专属价 30 <br> 2. 点击保存 <br> **场景二（等于底价，边界值）**：3. 填写专属价 50.00 <br> 4. 点击保存 |
```

### 4.3 禁止写法

| 禁止 | 原因 | 替代写法 |
|:--|:--|:--|
| `- 步骤一` | Parser 无法识别无序列表 | `1. 步骤一` |
| 步骤与预期混写 | 导致输出结构不清晰 | 步骤只写操作，预期只写结果 |
| `预期：xxxx`（正文嵌入）| Parser 无法独立提取 | 必须写在 `**预期结果**` 字段行内 |

## 五、财务专有属性规范

凡涉及以下场景，**必须** 在预期结果中写明计算公式或精度要求：

### 5.1 必须写明计算公式的场景

| 场景 | 要求 | 示例写法 |
|:--|:--|:--|
| 残值计算 | 写明公式：`残值 = 剩余天数/总天数 × 历史实付` | `残值 = 200/365 × 5000 = 2739.73 JPY` |
| 补差价 | 写明：`应付 = 新卡费 - 残值` | `应付差价 = 8000 - 2740 = 5260 JPY` |
| 溢转金额 | 写明：`溢转 = 残值 - 新卡费`，并注明精度 | `溢转 4671 JPY 1:1 转入 B2B 余额` |
| 汇率换算 | 写明公式，并注明精度 | `CNY = JPY / (基准价 + 0.75)` |

### 5.2 精度要求表

| 币种 | 无损精度标准 | 特殊说明 |
|:--|:--|:--|
| JPY | 取整（无小数） | 向下取整，禁止 0.x 碎数残留 |
| USD | 保留 2 位小数 | 四舍五入，禁止截断 |
| KRW | 取整（无小数） | 同 JPY |
| CNY（底座） | 保留 2 位小数 | 内部记账字段，统一 2 位 |

### 5.3 财务类预期结果必须包含的断言

```
✅ 金额计算值（含具体数字）
✅ 精度/取整规则描述
✅ 账户归属（会员费账户 / B2B余额 / B2B可提现余额 三者严格区分）
✅ 禁止事项（如"不吞没"、"不出现账目黑洞"）
```

## 六、标准模板示例

以下为一条合规用例的完整示例供参考：

```markdown
#### TC-FI-008 【重点·正向】升级补差价：残值计算公式验证

| 字段 | 内容 |
|:--|:--|
| **测试点** | 会员升级补差价 - 残值 = 剩余天数/总天数 × 历史实付会员费（取历史价格快照，非当前配置价）|
| **优先级** | Critical |
| **前置条件** | 用户已购买 EC 会员（1年=365天，实付 5000 JPY）；当前剩余 200 天；VIP 新卡费 8000 JPY |
| **操作步骤** | **场景一（1年期，分母=365）**：1. 用户发起升级 VIP 操作 <br> 2. 查看系统展示的应付差价计算明细 <br> **场景二（5年期，分母=1825）**：3. 准备一个购买了"5年期"EC会员（总天数1825）并已过1年（剩余1460天）的测试账号 <br> 4. 发起升级 VIP，查看差价计算明细中的分母取值 |
| **预期结果** | 场景一：残值 = 200/365 × 5000 = 2739.73 JPY（JPY取整 = 2740）；应付差价 = 8000 - 2740 = 5260 JPY；场景二：系统分母自动取 1825 天（非固定 365），残值 = 1460/1825 × 历史实付，精确计算；两场景均使用历史实付价快照，不取当前配置价 |
| **财务精度** | JPY 取整（向下），禁止出现小数；历史实付以数据库 `order_price_snapshot` 字段为准，不取 `current_price` |
```

## 七、避坑指南（Parser 常见解析错误）

| ❌ 错误写法 | ✅ 正确写法 | 原因 |
|:--|:--|:--|
| 表格单元格内使用 `\|` | 使用 `&#124;` 或改写句子避开竖线 | 未转义竖线破坏 Markdown 表格结构 |
| 步骤用中文顿号：`一、` | 改为 `1.` | Parser 只识别数字序号 |
| 预期结果写 `见步骤3` | 直接写出对应预期内容 | 引用式写法 Parser 无法独立提取 |
| 用例标题含冒号 `：` | 改为空格或破折号 | 部分 Parser 将冒号解析为 YAML 键值对 |
| 多条用例写在同一 `####` 块内 | 每条用例独占一个 `####` 锚点 | 锚点重复导致 Parser 索引错乱 |
| 优先级写 `P0` / `P1` | 统一写 `Critical` / `High` | 枚举值不在约定范围内 Parser 报错 |
| 预期结果只写"成功"两字 | 写明具体数值/状态/字段变化 | "成功"无法作为断言条件 |
| 前置条件留空 | 写 `无特殊前置条件` | 空值字段将被 Parser 跳过导致解析缺失 |

## 八、一致性自检清单

提交用例前，请逐条过一遍：

- [ ] 测试点开始前，已书写了外部分类层级锚点（`## [测试点名称]`）
- [ ] `####` 锚点格式符合 `TC-{模块代码}-{三位编号} 【{类型}】{标题}`
- [ ] 5 个必填字段全部存在（测试点 / 优先级 / 前置条件 / 操作步骤 / 预期结果）
- [ ] 操作步骤使用数字序号，多步骤用 `<br>` 分隔
- [ ] 预期结果与操作步骤数量对应，无遗漏
- [ ] 涉及金额计算时写明公式 + 精度规则 + `**财务精度**` 扩展字段
- [ ] 优先级取值在枚举表内（`Critical / High / Medium / Low`）
- [ ] 表格内无未转义竖线 `|`
- [ ] 前置条件非空
