# 上线验收测试报告规范

本规范用于 Agent 1 在用户要求“输出测试报告 / 出具验收报告 / 生成上线验收测试报告”时执行。目标是沉淀与 `黑白名单及采购账号` 项目一致的 Markdown 与 PDF 报告格式，并支持从测试用例 Excel、缺陷 RTF、Agent2 执行报告等多源数据聚合。

> 轻量场景可使用同目录下 `简易测试报告模板.md`。该模板固定只保留：测试结论、项目基础信息、测试环境、测试范围、缺陷明细。

## 1. 相关文件

Agent 1 生成报告前，按项目目录优先读取以下文件：

| 类型 | 文件路径或匹配规则 | 用途 |
|---|---|---|
| 项目需求 | `{项目}/测试文档/`、`{项目}/` 下的 PRD、技术方案、需求说明、会议纪要 | 确认项目范围、模块名称、上线背景 |
| 测试规约 | `{项目}/测试文档/superpowers.md` | 生成核心规约验收审计 |
| 测试大纲 | `{项目}/测试文档/测试点大纲.md` | 生成覆盖维度与模块覆盖表 |
| 测试用例 | `{项目}/测试文档/{项目名}测试用例.md`、`{项目}/测试文档/special_*测试用例_*.xlsx` | 统计用例总数、通过数、失败数、阻塞数 |
| 工期评估 | `{项目}/测试文档/工期评估.md` | 生成项目与工期概况 |
| 执行交接 | `{项目}/测试文档/执行交接清单.yaml` | 核对用例总量、优先级分布、执行范围 |
| Agent2 执行结果 | `{项目}/测试文档/执行报告/执行报告_*.md`、`{项目}/测试文档/执行报告/缺陷清单_*.md` | 聚合执行结果与缺陷闭环 |
| 缺陷导出 | `{项目}/测试文档/协润进出口_缺陷_*.rtf` | 统计缺陷类型、等级、状态、遗留风险 |
| 公共脚本目录 | `00_全局测试规约库/工具脚本/上线验收报告/` | Agent 1 生成与校验报告时优先调用 |
| PDF 转换脚本 | `00_全局测试规约库/工具脚本/上线验收报告/md_to_pdf.py` | 复用 PDF 版式 |
| PDF 渲染脚本 | `00_全局测试规约库/工具脚本/上线验收报告/render_pdf_pages.py` | 将 PDF 页面渲染为 PNG 进行视觉核对 |
| PDF 参考样式 | `黑白名单及采购账号/测试文档/上线验收测试报告（采购账号）_20260429.pdf` | 核对标题、摘要框、表格、分节样式 |

输入源优先级：

1. 若存在最新 `special_*测试用例_*.xlsx`，以 Excel 的执行状态作为用例统计主数据源。
2. 若存在最新 `协润进出口_缺陷_*.rtf`，以 RTF 的缺陷记录作为缺陷统计主数据源。
3. 若存在 Agent2 的 `执行报告_*.md` 与 `缺陷清单_*.md`，应合并引用，用于补充执行过程、证据与风险说明。
4. 缺少 Agent2 执行报告时，不应直接中断；只要存在可计算的 Excel、RTF 或人工确认结果，即可生成报告，并在“数据来源”中说明来源。
5. 若没有任何执行结果来源，才中止并提示需要补充执行数据。

## 2. 报告文件与落点

报告必须输出到对应项目的 `测试文档/` 目录：

| 文件 | 命名 |
|---|---|
| Markdown | `上线验收测试报告_YYYY-MM-DD.md` |
| PDF | `{项目名}_上线验收测试报告_YYYY-MM-DD.pdf` |

生成 PDF 后，可同步复制一份到 `output/pdf/`，便于集中归档。PDF 必须渲染检查至少首页与关键数据页，确认标题、摘要框、表格、分页无明显错乱。

## 3. Markdown 固定结构

报告正文必须采用以下结构：

```markdown
# 🚀 项目验收测试报告：{项目名}

> **报告摘要：**
> - 测试结论：<span class="pass">✅ 测试通过</span>（或附条件上线 / 暂缓上线）
> - 当前阶段：{SIT/UAT/上线验收/回归测试} 测试完毕
> - 发布建议：{明确上线建议}

## 1. 项目与工期概况 (Project Overview)

## 2. 测试覆盖与执行量化 (Execution Metrics)

### 2.1 核心需求模块覆盖率

### 2.2 用例执行结果统计

### 2.3 测试对象与文件覆盖

## 3. Superpowers 核心规约验收审计

## 4. 已知问题与遗留风险

## 5. 上线注意事项 / 生产运维预案

## 6. 变更记录
```

要求：

- 标题、摘要框、一级章节、表格样式参考采购账号 PDF。
- 摘要结论通过时使用 `<span class="pass">✅ 测试通过</span>`。
- 章节内容必须以表格为主，避免散文式堆叙。
- 变更记录至少包含报告生成日期、数据来源、统计口径。

## 4. 统计口径

| 指标 | 规则 |
|---|---|
| 用例总数 | 以最新有效测试用例 Excel 或交接清单为准；用户明确删除的用例不计入有效范围 |
| 通过数 | 状态为通过、Pass、已通过或用户明确确认通过的用例 |
| 失败数 | 状态为失败、Fail、未通过且仍需处理的用例 |
| 阻塞数 | 状态为阻塞、Blocked、无法执行的用例 |
| 通过率 | `通过数 / 有效用例总数`，保留 1 位小数或按报告现有风格展示 |
| 测试对象 | 按实际对象计数，如表单文件、面单、模板、导入模板、接口、页面等，不得漏计 |
| 缺陷总数 | 以最新缺陷 RTF 或缺陷清单为准，区分 BUG 与优化项 |
| 严重等级 | 统计 Critical、High、Medium、Low；中文等级映射为致命、严重、一般、低 |
| 缺陷状态 | 区分已关闭、已拒绝、处理中、待验证；已拒绝的重复单或非问题不列为遗留风险 |

用户明确说明“不做处理 / 不需要体现 / 非问题”的事项，不写入测试报告的问题与风险章节。

## 5. 缺陷章节写法

“已知问题与遗留风险”只展示上线相关的真实风险：

- 已全部关闭时，写明缺陷闭环总量、BUG/优化项数量、严重等级分布、关闭/拒绝数量，并给出“无开放阻塞问题”的结论。
- 存在未关闭缺陷时，按严重等级降序列出问题、影响范围、当前状态、上线建议。
- 已拒绝的重复问题、动态数据差异、非功能性口径差异可计入统计，但不作为开放风险展开。

## 6. PDF 生成要求

优先调用 `00_全局测试规约库/工具脚本/上线验收报告/md_to_pdf.py` 的版式。若项目路径包含中文导致 Playwright 或临时 HTML 处理异常，可将 Markdown 与转换脚本复制到 ASCII 临时目录完成转换，再把 PDF 回写到项目 `测试文档/`。

PDF 验证步骤：

1. 生成 PDF。
2. 调用 `00_全局测试规约库/工具脚本/上线验收报告/render_pdf_pages.py` 渲染首页与关键统计页为 PNG。
3. 检查标题、摘要框、章节编号、表格边框、分页是否与采购账号报告一致。
4. 若 PDF 失败但 Markdown 已完成，必须在最终说明中标记 PDF 未生成原因。

## 7. 发布建议判定

| 判定 | 条件 |
|---|---|
| 具备上线条件 | 有效用例全部通过，Critical/High 阻塞缺陷为 0，核心规约通过 |
| 附条件上线 | 核心链路通过，但存在不阻塞上线的 Medium/Low 遗留项，且有明确规避或跟进计划 |
| 暂缓上线 | 存在未关闭 Critical/High 缺陷、核心链路失败、数据安全或权限边界未通过 |
