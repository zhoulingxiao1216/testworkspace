# 测试点大纲编写规范

> 本规范由「会员体系优化」测试大纲实例归纳而来，适用于所有新需求的测试点大纲编写。

---

## 一、文档结构总览

```
# [需求名称] 测试点大纲

> [文档背景说明：基于哪些材料整理、特殊约定（如去除哪些场景）]

## 测试前置条件
  ### 测试账号准备（按维度分组）
  ### 管理端/环境配置前置
  ### 特殊模式/场景说明

---

## 测试核心原则（必读）
  [原则1] ...
  [原则2] ...
  ...

---

- [需求名称]测试点
  - [模块A]
    - [子模块A1]
      - 测试点1
      - 测试点2（含验证点缩进）
    - [子模块A2]
      ...
  - [模块B]
    ...
```

---

## 二、各章节编写要求

### 2.1 文档头部

| 字段 | 格式 | 说明 |
|:---|:---|:---|
| 标题 | `# [需求名称] 测试点大纲` | 与需求/PRD名称保持一致 |
| 引用说明 | `> 基于XXX整理，已确认XXX` | 说明来源材料及特殊决策 |

---

### 2.2 测试前置条件

#### 测试账号准备

- 按**业务维度**（国家/角色/环境等）分组，使用表格展示。
- 表头示例：`| 维度 | 参数 | 需要的账号类型 |`
- 账号类型注明**数量**（`× N`）和**用途说明**。

```markdown
| 国家 | 币种 | 需要的账号类型 |
|:---|:---|:---|
| 🇯🇵 日本 | JPY | 普通用户 × 1、EC会员 × 1、VIP × 1 |
```

#### 管理端/环境配置前置

- 使用无序列表（`-`），逐条列举测试开始前必须完成的配置项。
- 每条需明确**作用范围**和**最低要求**（如「至少覆盖X种模式」）。

#### 特殊模式说明

- 使用 `>` 块引用 + 加粗关键词突出特殊约定。
- 对不同维度（如多国）分别说明其测试模式及重点验证方向。

---

### 2.3 测试核心原则（必读）

- **目的**：明确该需求的业务约束边界，防止测试遗漏或方向错误。
- **写法**：逐条加粗命名：`**原则N：[原则名称]**`，下方用 `-` 展开说明。
- **数量**：通常 3～6 条，覆盖：权限隔离、数据隔离、优先级规则、历史快照/防改价等。
- **原则范式**（参考）：

| 原则类型 | 典型内容 |
|:---|:---|
| 维度隔离 | 不同国家/角色/环境下数据独立，不允许互串 |
| 权限准入 | 区分哪些用户有哪些操作权限及拦截节点 |
| 价格优先级 | 明确各类价格的覆盖顺序（专属价 > 等级价 > 默认价） |
| 历史快照 | 已生成单据/订单，后台改价/改级后不受影响 |
| 实时生效 | 配置变更后前台缓存清除时效要求 |

---

### 2.4 测试点列表

#### 层级结构

使用**无序嵌套列表**，统一缩进层级规则：

```
- [需求名称]测试点          ← Level 0（固定根节点）
  - [模块]                  ← Level 1（按业务域划分，如：管理端/客户端）
    - [子模块]              ← Level 2（按功能页面/功能区划分）
      - 测试点描述          ← Level 3（一条可执行的测试动作+预期结果）
        - 验证点：...       ← Level 4（仅在需要拆解多个验证维度时使用）
```

#### 模块划分原则

| 模块类型 | 划分依据 |
|:---|:---|
| 按端划分 | 管理端 / 客户端 / 跨端验证 |
| 按页面划分 | 与UI原型/PRD章节对应 |
| 按生命周期划分 | 创建 / 使用 / 到期 / 续费 / 降级 |

#### 测试点描述规范

- **描述粒度**：一条测试点 = **一个操作 + 一个预期结果**，可执行、可验收。
- **禁止模糊描述**：不写「验证功能是否正常」，要写「输入X后点击保存，系统显示Y提示」。
- **使用`【重点】`标记**高风险测试点（业务损失风险大、历史Bug高发、边界条件复杂）。
- **验证点缩进**：当一个测试点需拆分多个检查维度时，用下一级 `-` 列出独立验证点。

#### 高风险标记标准

以下场景**必须**标注`**【重点】**`：

| 场景类型 | 示例 |
|:---|:---|
| 金额/财务计算 | 溢转、差价、汇率锁定 |
| 数据隔离/防串 | 多租户/多国/多账号切换后缓存彻底清除 |
| 权限边界 | 无权限用户操作拦截是否有效 |
| 历史快照保护 | 改价/改级后已有单据不变 |
| 时效性 | 跨日操作、定时上架、过期自动降级 |
| 配置上限 | 最多N条时第N+1条的置灰/报错 |

#### 计费/数值类测试点模板

```markdown
- **【重点】** [场景描述]
  - 验证点：[数值A] [运算关系] [数值B] 时，[操作]，系统[预期结果]
  - 验证点：边界值（=[临界值]）时，[预期结果]
  - 验证点：反向（[数值A] [反向关系] [数值B]），保存时[报错/拦截]
```

#### 缓存实时性测试点模板

```markdown
- [配置变更操作]，前台[对应展示]实时刷新（含缓存清除验证）
```

## 三、格式规范速查

### Markdown语法约束

| 元素 | 规范 |
|:---|:---|
| 标题 | 仅用 `#` / `##` / `###`，不超过三级 |
| 表格 | 表头左对齐（`:---`），正文简洁 |
| 重点标记 | `**【重点】**`，位于测试点描述行首 |
| 分隔线 | 模块间用 `---` 分割（前置条件、核心原则各一条） |
| 引用块 | `>` 仅用于文档说明和模式注解 |
| 列表缩进 | 统一使用2个空格缩进 |

### 内容完整性 Checklist

在提交大纲前，逐项确认：

- [ ] 文档头部有背景说明和特殊约定
- [ ] 前置条件覆盖：账号准备 + 环境配置 + 模式说明
- [ ] 核心原则已列出，且原则间无遗漏重叠
- [ ] 测试点按端/模块/子模块三级划分清晰
- [ ] 所有金额计算场景已标注`【重点】`
- [ ] 所有数据隔离/缓存场景已标注`【重点】`
- [ ] 边界值（最大值+1、零值、负值、跨日等）已覆盖
- [ ] 计费模式全路径（每种模式至少一条测试点）已覆盖
- [ ] 权限准入拦截点已明确（非购物车或指定页面）
