# 全球站项目：会员与服务体系优化 PRD

## 1. 项目背景与目标

### 1.1 项目背景
目前我们的全球站项目中，所有的国家都在使用同一套会员等级和附加费定价规则。随着海外业务在不同国家的拓展，这种“一刀切”的设计带来了一些实际业务问题：
1. **无法满足不同国家的本地化运营需求**：我们需要能为每个国家单独设置不同的会员费、价格梯度、服务费以及支持的币种。
2. **结算与退款逻辑缺乏历史溯源**：目前的系统在升级、过期以及发起售后退款时，没有严格隔离购买时的“历史价格记录”，容易导致按最新价格退旧单的财务对账不一致或用户套现问题。

### 1.2 优化目标
1. **实现“基础库+国家配置”的分离架构**：把所有的附加项、检品分类等信息统一在“基础库”中维护。每个国家站点单独挑选所需的服务，并单独设置售价。
2. **规范化会员身份与购物车准入门槛**：
   - **会员身份划分**：系统包含“一般会员”、“EC商务会员”、“EC&OEM商务会员”、“VIP会员”。若用户没有任何以上头衔，则属于“普通用户”。
   - **核心入口准入规则**：**只有拥有会员身份才能完成最终的加购下单行为。对于无身份的“普通用户”，系统允许其正常进入“购物车”、“个人中心”、“重要代办”等关联业务版块进行浏览与操作，但绝对禁止其进行最终的提单与下单动作！**
   - **一般会员兜底防线**：若当前运营国家后台上架了“一般会员”等级，用户注册后将自动获取“一般会员”身份，从而直接获得下单资格（无需充值）；若该国未配置上架“一般会员”，则新注册的用户只是“普通用户”，可正常访问主要板块，但一旦尝试点击结算动作，必须被强制拦截并跳转充值成为付费会员后，方可下单购物。
   - 所有包月的会员时长固定按“30天/月”计算，时间精度采用精确到秒的 Timestamp 进行 30*24*3600 顺延累加，不使用自然日。
   - 支持会员升级（补差价，原天数按购买价折算抵扣后重置）和同级续费（天数合并累加），**不允许用户主动降级操作**。
     - **【余额溢转兜底机制】**：在计算会员升级补差价时，如果原卡剩余天数所折算出的残值金额 **大于** 升级后新会员阶梯的待支付全款额度（即抵扣后差价呈现负数），系统应当正常为其开通新身份；**并将该溢出未扣完的剩余差价部分，以 1:1 的价值全额折算为对应的资金，系统自动充值退回存放至该买家的 B2B 余额（Balance）钱包中**，绝不可发生资产吞没或硬性抹零！
3. **支持多种灵活的业务计费模式**：系统全面支持“阶梯价”、“普通”、“起订量”、“按套”、“按时”、“相谈”、“仓储”等多维计费模式。
4. **规避隐性资金与缓存问题**：
   - 线下对公打款充值的会员充值金，必须同可提现的余额（Balance）严格分开。
   - 所有报价单和退款，必须严格按照当时的订单历史价格进行计算。

#### 2.3.1 编辑全球服务定价.html

**① 核心业务逻辑介绍**
定义全平台附加服务的具体计费公式。本页面突破了传统的表单限制，采用**全屏弹窗选品 + 左右分栏交互**的大型配置器框架结构。

**全局交互核心**：
1. **全屏检录大盘**：为了缓解视觉压力与方便海量勾选，用户点击“全屏”按钮后，将铺开一个完整覆屏的源池面板，此处收录了全球维度启用的所有 `检品方式` 与 `附加项`。完成勾选操作后数据同步收纳回主流程工作台界面的“应用中”项目内。
2. **左右双轴工作台**：页面左侧罗列树状结构的已勾选服务分类（其中括号内的数字动态表征当前激活加载的数量，例如 `附加项 (5)`）。只要在左边点击确切的服务单元，右侧作业主轴即刻展开并响应展示该服务项的专有配置参数（包括但不限于：应用状态、排序属性、精准计费逻辑表）。

**② 高级机制其一：多维会员身份矩阵定价 (跨模块强联动)**
服务的单价并非单薄的一维数字。它受到上游【2.2.1 编辑全球会员定价】中针对该国所配置的“已激活会员身份”严格制约发散。
- **表单区块动态裂变**：假设当前编辑的国家（如美国）在总盘总共启用了 3 种会员等级（例如：`一般会员`、`EC商务会员`、`VIP会员`），那么界面的右侧下半部分，**所有与钱和阶梯起订量相关的参数结构，都必须针对这 3 种身份循环复制并展示出 3 套完全平级、结构相同的金流录入框组**。
- **定权隔离计价**：运营针对同一个附加项，必须对这 3 个身份分别独立报盘定价，确保高等级的会员身份能在底层享用到低廉的工时或质检专属服务价。所有后续提到的“客户单价”均依托会员级别阵列存在。

**③ 字段级别功能描述与异常流程（基辅六大计费体系底座）**

| 字段/控件名称 | 功能展现描述 | 业务规则与异常边界处理 |
| :--- | :--- | :--- |
| **元数据维护台** | 挂载所选主服务的 `状态` (启用/禁用) 与决定界面展示顺位的 `排序` 输入项。 | - |
| **多语系拓展：介绍页面描述** | 携带 `展开翻译` 控件的核心多文本矩阵场，用于补充前台各细分动作的营销释义。 | 要求在此实现英文、日文及特定7国语言维度的平级分化文本表。需在后库拦截校验超长恶意攻击注水字符或XSS入侵。 |
| **计费逻辑（定基核算核源）** | 下拉框形态，统御整套金流运算模型的司令塔中枢。 | **动态锁权机制**：若左侧源选品为“检品方式”，此框严禁显示额外项，锁定只下发 `普通 / 按套 / 按时 / 相谈 / 仓储` 等基础维度；若源自“附加项”，才能全量开放出包含阶梯等在内的流派选择权。 |

**④ 专项剖析：六大核心计费逻辑表单字段衍变表**
根据管理员在 `计费逻辑` 下拉框中点选的不同模式，右侧表单将发生**剧烈的结构形变**，具体渲染的字段要求如下：

| 计费逻辑模式 | 触发场景与定义 | 专属动态渲染的表单字段群 | 逻辑底线与边界拦截 |
| :--- | :--- | :--- | :--- |
| **1. 普通** | 最基础的一口价线性服务标价。 | `成本单价`、`客户单价`。 | **利润红线**：严禁提交 `客户单价 < 成本单价` 的负利润配置。 |
| **2. 阶梯** | 依量砍价的批发型逻辑。 | `起步数量区间框 (例如 ~以上)`、对应的 `成本单价` 与 `客户单价`。<br/>自带 `[+添加阶梯]` 动态无限增殖行按钮。 | **防死锁算法**：保存时必须在后端进行跨阶梯校验。禁止出现“大区间价格反超小区间（价格倒推）”，同时也禁止“区间数量交叉（如写了 50~以上，下一行写 40~以上）”，一旦发现直接飘红弹回。 |
| **3. 起订量** | 带有强硬起步门槛的重型施工项。 | 独有字段 `起订数量 (件)`。<br/>常规呈现 `成本单价`、`客户单价`。 | 约束前端收银台逻辑：买家在该 SKU 上的投检数量若未满这里的 `起订数量`，则系统强行按这个最低阈值乘以单价扣减。 |
| **4. 按套** | 将零散 SKU 打包为一整个实体动作包收费。 | 独有字段 `包含件数 (/套)`。<br/>常规呈现 `成本组合单价`、`客户组合单价`。 | 前台算费需引入取整逻辑（向上取整）：例如配了 5件/套，买家提交 6 件，则系统直接按 2 套计扣费。 |
| **5. 按时** | 纯工时租赁或计时观测性质的维保动作。 | 基础渲染 `成本时价`、`客户时价`。 | 此模式的实际“单位（如 0.5H 或 1H）”早已在【2.0 主库】内被写死限制，此处只配单价，不配单位系数。 |
| **6. 相谈** | 用于无法通过标准化算本估价的极度定制级业务。 | **绝对零字段**。系统直接折叠并隐藏所有的成本、客户价等金额类 Input 框。 | 前端收银台针对此项仅展示为“另行报价 / 面议”，不纳入在线即时收银结算金流总库。 |

## 4. 其他关联模块 (连带核心后端系统影响与阻击规范)

本次大范围的前端功能收口与优化动作，对后端的**订单、报价单、资金流**等核心链路产生了高度强制的隐性防线要求。为防止“前端锁死，后端放行”导致越权重灾区，特列举以下底层模块影响列表，这必将作为后端 API 安全测试的红线验收指标：

| 前端表现 / 用户侧操作 | 潜在漏洞与防线断层风险点 | 核心关联的后端微服务及硬性加固要求 |
| :--- | :--- | :--- |
| **【3.3 购物车非会员拦截】**<br/>若为普通用户，购物车“下一步”按钮被锁上无法点击。 | **抓包绕过提单**：只靠前端置灰 UI，极易被懂技术的客群拦截发包指令，用脚本强行调用原本通畅的订单生成接口。 | **【全链路下单验证网关】**<br/>必须在接收到结算提单请求时，加挂**身份重验中间件**。一旦发现是无卡的普通用户越权，后端接口必须强力回吐 `Http 403`，直接阻断业务落库，绝不留后门。 |
| **【3.1.1 汇款入金闭环】**<br/>汇款页面金额外显为只读数值，彻底被剥夺手动输入框权限。 | **恶意低价充值**：如果不做强制干预，黑客可通过 Postman 等发包发送 1 JPY，骗取后台充值微服务过账来套现高等级 VIP 卡卡种。 | **【支付核销微服务 / 资金回调池】**<br/>后端**彻底剥夺前端在此环节定价权**。接口必须无视并拒收该来源的 `amount` 值，且只能通过传来的 `国家ID` 与 `会员层级ID` 去反查 2.2.1 的主配置库来提取底价，通过此官方底价生成待核销台账单据。 |
| **【2.4 私定大客明细】**<br/>大客一旦修改了附加项，后台对其详情即刻进行异样告警标红。 | **无差别渲染失败**：前端拿不到参考的比照基线，完全无法在底层启动条件渲染指令，导致 UI 全都是黑字而分辨不住哪些被私下更改过。 | **【客户个性大宽表查询流】**<br/>除输出折扣的数字外，后端在此列表的接口 DTO 里必须增加 `is_custom_price (布尔值)` 作为明确开关，或者连带原始公版价双轨吐出来，供该节点的前端组件用作 `class="red"` 的 `v-if` 对冲校验。 |
| **【核心履约案卷档】**<br/>各类已经清算或定型的历史案卷展示，全程断绝二次动态获取或连查。 | **配置表异波连爆事故**：管理员在后台因为节假日上调单价后，过去老版本的报价单或订单也跟着涨价了，引起全局性质的财务对账假账。 | **【全生命周期 DB 快照固化域】**<br/>当任何订单或报价单进入定格态等生命终极钩子，后端必须把当时引用的各类计件逻辑、基础价格等配置全套通过序列化转化为 **静态 JSON 快照字符串数据 `snapshot_data`** 强行塞入副表字段。往后所有列表、详情流只许读快照！ |
